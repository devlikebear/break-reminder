# 집중·시간 도구 확장 — 개발 로드맵

작성일: 2026-09-28 · 기준 HEAD: `8e8cb795f6570adc2bc602d4124264f9e64baee8`

상태: **구현 전 개발계획**. 사용자 요청은 심층 기획이며 이 문서의 체크박스는 구현 완료를 의미하지 않는다. 코드·서비스·사용자 설정 변경, 커밋·배포는 이번 산출물에 포함하지 않는다.

## 1. 제품 방향

Break Reminder를 일하다가 휴식 알림을 받는 도구에서, 사용자가 집중 주기와 짧은 작업 시간을 직접 시작하는 메뉴바 도구로 확장한다. 기존 햄스터·휴식 화면·작업 통계는 유지한다. 새로운 계정, 서버, AI 기능, 외부 의존성은 필요하지 않다.

첫 배포의 범위는 **기존 포모도로의 GUI 접근성 개선 + 이름 있는 일반 타이머 1개**다. 스톱워치와 시각 알람은 후속 배포 단위다. 네 기능을 모두 첫 배포에 넣지 않는다.

핵심 사용 사례:

- 개발 시작 전 메뉴바에서 포모도로를 켜고 오늘 완료한 회차를 확인한다.
- 코드 리뷰 15분, 차 우림 5분처럼 이름과 시간을 지정하고 다른 작업으로 돌아간다.
- 후속: 예상 시간이 없는 작업을 스톱워치로 측정하고 기록한다.
- 후속: 특정 날짜·시각에 회의 준비 알람을 예약한다.

활용도 향상은 가설이다. 원격 분석을 추가하지 않고, 첫 배포 후 1주 동안 사용자가 실제 사용 여부·재사용한 프리셋·알림 누락 여부를 확인한다. 기능이 완성됐다는 사실과 사용 빈도가 늘었다는 결과를 구분한다.

## 2. 현재 구현에서 출발하는 결정

상세 근거: [코드베이스 분석](time-tools-codebase-analysis.md).

1. 포모도로 25/5/15·4회 주기는 이미 Go에 있다. 새 엔진을 만들지 않는다.
2. 기존 포모도로는 **활동 감지 기반**이다. 유휴·자연 휴식·근무 세션 정책의 영향을 받으며 일반적인 25분 벽시계 카운트다운과 다르다. 첫 버전 UI에 이를 표시한다. 고정 경과시간 포모도로는 별도 후속 과제로 남긴다.
3. 일반 타이머는 업무 세션·요일·일시정지·휴식 화면과 독립적이어야 한다. 기존 `timer.Tick`에 넣지 않는다.
4. 기존 휴식 check는 launchd 60초 주기이며 block 화면을 기다릴 수 있다. 초 단위 완료는 **Aqua 사용자 세션의 별도 launchd Go worker**가 담당한다. `RunAtLoad`/`KeepAlive`로 유지하고 매 약 1초 `time.Now().UnixMilli()`와 저장한 deadline을 비교한다. 메뉴바 자식 프로세스로 실행하지 않는다.
5. 새 영속 데이터는 기존 `~/.break-reminder-state`와 분리된 `~/.config/break-reminder/time-tools.json`에 둔다. Go만 flock 안에서 ID/revision을 검증하고 수정한다. Swift의 기존 Reset/Force Break가 새 데이터를 지우지 못하게 한다.
6. 스톱워치 기록은 기존 자동 업무 통계에 합산하지 않는다. 겹치는 시간을 중복 계산하지 않기 위해 통계 합산 기능 자체를 이번 로드맵에서 제외한다.

## 3. 범위와 우선순위

| 단계 | 사용자에게 완결되는 결과 | 범위 | 예상 공수 |
|---|---|---|---|
| 1 | 메뉴바/대시보드에서 포모도로 선택·시작·회차 확인 | 기존 엔진 UI, 명령 오류 표시, 입력 단축키 보호 | 12–20시간 |
| 2 | 앱 창을 닫아도 이름 있는 타이머 완료를 확인 | 단일 타이머, worker 설치·업그레이드 전환, 알림 실패·overlay UX, 두 UI | 32–50시간 |
| 3 | 작업 소요 시간을 측정하고 로컬 기록 | 단일 스톱워치, 일시정지, 저장/삭제 | 12–20시간 |
| 4 | 날짜·시각을 지정해 1회 알람 예약 | 최대 10개, 시간대 표시, 지난 알람 처리 | 16–24시간 |

공수는 1인 구현·테스트·수동 QA를 포함한 계획용 추정이다. 첫 배포 44–70시간, 전체 72–114시간이며 달력상 납기 약속이 아니다. 서비스 생명주기와 실제 알림 QA가 가장 큰 불확실성이다.

의존 관계: `1 → 2 → 1주 사용 검증 → go/no-go → 3 또는 4`. Phase 3은 Phase 2의 저장소·CLI·UI를 재사용하므로 의존하며 **worker 없이 동작**한다. Phase 4는 Phase 2의 worker/event에 의존하며 Phase 3 구현은 선행 조건이 아니다. 기본 순서는 3→4지만 각 단계의 사용 가치를 따로 판단한다.

### 후속 개발 go/no-go

첫 배포를 1주 사용한 뒤 `time-tools-validation.md`에 실제 사용일·사용 사례·실패/누락·재사용 여부를 기록한다. 원격 텔레메트리는 추가하지 않는다.

- **Go 공통 조건:** 데이터 유실/중복 완료/설명 없는 알림 누락이 해결되고, 사용자가 유지할 실제 사용 사례를 확인한다. 단순 설치나 테스트 실행 횟수는 활용도로 세지 않는다.
- **Phase 3:** 통계 합산 없이도 과거 작업 소요 시간을 다시 보는 구체적인 사용 사례가 있을 때 진행한다. 기록을 다시 볼 필요가 없다면 스톱워치 기록 기능을 축소하거나 단계를 보류한다.
- **Phase 4:** 상대 시간 타이머로 해결되지 않는 날짜·시각 예약 수요가 있을 때 진행한다.
- **No-go:** 사용 사례가 없거나 알림 신뢰성 문제가 남으면 3·4를 자동 구현하지 않고 첫 배포 개선에 집중한다. 기존에 전체 구현을 승인했더라도 이 제품 검증 결과를 먼저 보고하고 후속 범위를 확정한다.

## 4. 첫 배포의 완료 기준

- [ ] 포모도로 시작/전환 실패가 UI에 나타나고 성공한 상태만 표시한다.
- [ ] 타이머 5·10·15·30분 프리셋과 직접 입력, 이름, 일시정지/재개/취소/다시 시작이 동작한다.
- [ ] 일반 타이머는 업무 종료·휴식 일시정지·주말에도 동작한다.
- [ ] 메뉴바와 대시보드가 같은 타이머를 표시하며 두 창에서 동시에 조작해도 상태가 덮어써지지 않는다.
- [ ] 창 종료, 메뉴바 종료, worker 재시작, 잠자기 후 복귀 시 정해진 복구 정책을 만족한다.
- [ ] 휴식 전체화면이 열려 있어도 worker가 완료 상태를 저장하고 알림을 요청한다.
- [ ] `make test`, `make build` 통과 및 수동 QA 증거를 남긴다.
- [ ] README와 CHANGELOG의 Unreleased에 범위·사용법·알림 전제조건을 반영한다.

## 5. 범위 밖

- 여러 일반 타이머 동시 실행, 랩, 반복/요일 알람, 알람 snooze, 클라우드 동기화.
- 고정 경과시간 포모도로, 프로젝트별 청구 시간, 업무 통계 자동 합산.
- 전체 UI 리뉴얼, 새 캐릭터/이미지, TUI 도구 화면, 캘린더 연동, 음성 타이머 생성.
- 잠든 Mac 깨우기, 전원 꺼진 동안의 알림, 집중 모드를 우회하는 알림.
- 과거 분석의 모든 리팩터링/보안 항목 일괄 처리. 새 경로에 직접 영향을 주는 상태·오류·입력 문제만 포함한다.

## 6. 실행 규칙과 핸드오프

1. 구현 시작 전 `git status --short`와 기준 HEAD를 확인하고 변경 범위를 보고한다. `.analysis/`에는 추적 파일과 미추적 파일이 함께 있다. 기존 추적 분석 파일, 미추적 `.analysis/cache/` 및 두 분석 보고서, `.serena/`, 루트 이미지를 모두 보존한다.
2. 각 작업은 실패 테스트 작성·RED 확인 → 최소 구현 → GREEN → 정리 순서로 수행한다. 아래 계획의 테스트 이름과 새 파일은 제안 계약이다.
3. 단계별 Checkpoint에서 자동/수동 결과와 증거를 보고한다. 사용자가 전체 구현을 승인한 경우 이 보고를 거쳐 계속 진행한다. 단계만 요청한 경우 그 단계에서 종료하고 다음 범위를 확인한다. 반복 승인 대기를 작업 자체의 요구사항으로 만들지 않는다.
4. 실패하면 범위를 넓히지 말고 원인·영향을 기록하고 수정·재검증한다. 실제 실행을 못 한 항목은 `NOT RUN`이며 PASS로 바꾸지 않는다.
5. 커밋 시 `feat:`, `fix:`, `chore:` 규칙을 사용한다. PR 생성 시 그 시점의 템플릿을 확인하고 준수한다. 현재 `.github/`에는 PR 템플릿이 발견되지 않았다.
6. 배포는 구현 요청과 별도로 범위를 확인한다. 기존 `CLAUDE.md`의 release workflow를 사용하며 이 계획에서 버전 번호를 예약하지 않는다.
